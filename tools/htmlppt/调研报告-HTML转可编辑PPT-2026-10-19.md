## 0. 摘要：五条核心结论

**① "HTML → 可编辑 PPTX"全行业只有一条可行架构：受约束的 HTML 子集 + 无头浏览器量测 + 映射成原生 DrawingML 对象。**
Anthropic `html2pptx`、PPTAgent `html2pptx.js`、Hasasasa、dom-to-pptx、slidesmith、Slidev `pptx-editable` 全部收敛到这条。差别只在"量测后写哪一层"和"CSS 表达不了的部分怎么兜底"。
→ [Anthropic html2pptx 指南](https://github.com/anthropics/skills/blob/ef740771/skills/pptx/html2pptx.md)、[PPTAgent html2pptx.js](https://github.com/icip-cas/PPTAgent/blob/v1.1.38/deeppresenter/html2pptx/html2pptx.js)

**② 主流框架的 pptx 导出默认都是"整页截图"，可编辑是后补的、且都标着 experimental。**
Marp `--pptx` 把每页渲成 PNG 当 slide background（**没有任何文字对象**）；`--pptx-editable` 走 HTML→PDF→LibreOffice Impress 导入，官方自称 EXPERIMENTAL、保真更低、不支持备注。Slidev `export --format pptx` 官方原话是"所有幻灯片将导出为图片，因此文本将不可选择"；**直到 2026-09-16 的 53.0.0 才新增 `pptx-editable`**（PR [#2722](https://github.com/slidevjs/slidev/pull/2722) 已核实 merged，npm `@slidev/cli@53.0.0` 同日发布）。
→ [Marp CLI README](https://github.com/marp-team/marp-cli#convert-to-powerpoint-document---pptx-)、[Slidev 导出文档](https://sli.dev/guide/exporting)

**③ 头部团队用产品决策投了反对票：Manus 已放弃"网页生成 + 导出转换"，改为原生生成 .pptx。**
官方原文（2026-07-14）："以前，Manus 以网页格式生成幻灯片，并在导出时将其转换为 .pptx，**这可能会导致格式问题**。PowerPoint 模式完全跳过了网页层，直接生成 .pptx 文件。"（已逐字核实）
→ **含义**：HTML 是可编辑 PPTX 最好的"作者界面"，但必须被降级为**受约束的中间表示**，而不是自由的创作终点。

**④ Anthropic 官方 html2pptx 已弃用且不可商用，这是选型的硬约束。**
`html2pptx.tgz` 于 2026-02-04 打包进 pptx skill 后**同一天**被 commit `a5bcdd7e` 以 "Delete deprecated" 删除；当前官方"创建新 deck"路径改为直接写 pptxgenjs 脚本。LICENSE 为 Anthropic proprietary，**禁止复制、衍生、分发、商用**。另有隐患：PPTAgent 的 MIT `html2pptx.js`（2987 行）文件头自称 "Originally based on Anthropic Skills"，**许可链有瑕疵，不能直接复用**。
→ [LICENSE.txt](https://github.com/anthropics/skills/blob/main/skills/pptx/LICENSE.txt)

**⑤ "精确"必须被拆成三个指标分别承诺，其中只有两个能保证。**
- **几何精确**（对象坐标 ≤0.5px）：✅ 能保证，靠固定画布 + 整数 px + `EMU = px × 9525` 整除。
- **语义精确**（文字是 `<a:t>`、形状是 `p:sp`）：✅ 能保证，靠映射规则 + 导出后解包统计。
- **排版精确**（断行位置、行基线逐行一致）：⚠️ 只能"接近"。**本报告给出并把原型验证了唯一的破局手段：按浏览器视觉行硬断行**（每个视觉行拆成一个独立段落 `<a:p>`，行距用 `a:spcPts` 写死，`wrap="none"` + 关闭 autofit）。

**本机原型已经把这套跑通**：5 页 1280×720 HTML → 66 个原生形状 + 1 个原生表格 + 3 张真实图片 + 68 个文本 run（**文本字符覆盖率 100%**），SVG 图标 8/8 转成原生 `a:custGeom`、渐变转成原生 `a:gradFill`（**参考实现在这两处都是栅格化**），zip 39/39 条目 DEFLATE（PowerPoint「需修复」护栏），LibreOffice 回渲 5 页全部成功，像素 MAE 4.25。—— 详见 §6 与 `prototype/README.md`。

## 1. 问题界定：先把"精确"和"可编辑"定义清楚

这两个词在这个赛道被滥用得最厉害。**不定义清楚，验收就无从谈起。**

### 1.1 三个正交的"精确"

| 指标 | 定义 | 能否保证 | 决定因素 |
|---|---|---|---|
| 几何精确 | 每个对象的 `x/y/w/h` 与浏览器量测一致，误差 ≤0.5px | ✅ 能 | 固定画布、整数 px、EMU 整除 |
| 排版精确 | 同一文本框内断行位置、行距、行基线与浏览器一致 | ⚠️ 接近 | 视觉行量测 + 硬断行 + 行距绝对值 + 字体可用性 |
| 语义精确 | 文字是真文本、形状是真形状、图片是真图片 | ✅ 能 | DOM→原生对象映射 + 解包自检 |

### 1.2 四个等级的可编辑性（L0–L3）

| 级别 | 能力 | 用户能做什么 | 代表产物 |
|---|---|---|---|
| **L0** | 整页图片 | 什么都不能改 | Marp `--pptx`、Slidev 旧 `--format pptx`、AiPPT「图片集 PPT」、所有 PDF→PPTX |
| **L1** | 底图 + 原生文本框 | 改字、挪字框 | Hasasasa 的栅格兜底页 |
| **L2** | 原生形状 + 文本 + 图片 + 表格 | 改字、挪/改色形状、换图、改表格 | Anthropic html2pptx、Slidev `pptx-editable`、**本原型** |
| **L3** | L2 + 主题/母版继承 | 一键换主题、套版式 | 需要 `p:sldMaster` 主题投影；PPTAgent 模板路线天然是 L3 |

> **产品红线**：如果卖点是"导出的 PPT 能随便编辑"，用户一试动画和形状就会觉得被骗。准确说法是 **"导出的 PPTX 里，文字和形状都能直接改（L2）"**，并显式声明不做动画/母版/公式。

## 2. 全景：五条路线，一条能走

```
路线 A  整页截图        HTML → PNG → pptx（每页一张图）
路线 B  PDF 中转        HTML → PDF → LibreOffice Impress → pptx
路线 C  量测重建        HTML → 无头浏览器量测 → IR → 原生 DrawingML 对象   ← 唯一可行
路线 D  模板槽位        参考 PPT 抽 schema → 在真 PPT 上做编辑动作
路线 E  原生 OOXML 直出 不经过 HTML，直接生成 .pptx（Manus PowerPoint 模式）
```

| 路线 | 代表 | 可编辑性 | 保真度 | 稳定性 | 许可风险 | 判定 |
|---|---|---|---|---|---|---|
| A 整页截图 | Marp `--pptx`、Slidev 旧、`nlj626/html-to-pptx`、AiPPT 图片集 | **L0** | 高 | 高 | 低 | ❌ 不可编辑，直接出局 |
| B PDF 中转 | Marp `--pptx-editable` | L1–L2 不可控 | 中 | 低（官方 experimental） | 低 | ❌ 文字块/换行/图层由 LibreOffice 猜 |
| **C 量测重建** | Anthropic、Hasasasa、dom-to-pptx、Slidev 53、**本方案** | **L2** | 中高 | 中 | 各不同 | ✅ **唯一可行** |
| D 模板槽位 | PPTAgent 研究框架 | L3 | 中 | 中 | 低 | ⚠️ 版式自由度 = 模板库大小；可做"企业模板模式" |
| E 原生直出 | Manus PowerPoint 模式 | L2–L3 | 高 | 中 | 低 | ⚠️ 不是转换，是绕过 HTML。**战略信号** |

**结论**：选 C。但要把 C 从"库/脚本"做成"产品"，缺的三件事是：**输入契约、降级策略、Office 打开回归**。

## 5. 技术地基：三堵墙

### 墙一：文本度量 —— 这是所有工具"看着差一点"的头号原因

**同一个字符串，Chrome 与 PowerPoint 的排版宽度差约 2%**（Slidev 源码用 2% + 4px 的 headroom 对冲）。根因有五条：

1. **行距语义三方不一致**：`a:spcPct` 规范说是"文本尺寸的百分比"（ISO 29500 §21.1.2.2.11），PowerPoint 实现是"字体自然行高（ascent+descent+lineGap）的百分比"，LibreOffice 26.8 实测是"字号 ×1.2 的百分比"。
   → **硬规则：行距一律用 `a:spcPts`（绝对值），永不用 `spcPct`。**
2. **autofit 行为不可控**：`normAutofit` 的 `fontScale` 由 PowerPoint 在编辑/重排时动态计算，LibreOffice 则在渲染时自行重算缩小（本机实测 32pt 被缩到 11–12pt）。
   → **硬规则：一律 `<a:noAutofit/>`。**
3. **CJK↔拉丁边界**：LibreOffice 在 CJK 与 Latin 交界处自动加 **≈0.24em/处**（本机实测 `中文ABC` 32px：Chrome 124.91px vs LO 132.50px）。
4. **`letter-spacing` 计数不同**：CSS 在每个字符后加（含末尾），LO 只加 n−1 次（实测 10 字符 Arial + 10pt 字距：Chrome 336.03px vs LO 322.60px）。
5. **字体解析/替换**：`.ttc` 字体在 LO 里可能被换成完全不同的家族（实测 `Hiragino Sans GB` → `NotoSansCJKhk`，同串渲染宽 462.8px vs Chrome 528.3px，**−12%**）。

**破局手段：按视觉行硬断行。**
用 `Range.getClientRects()` 逐字素测出视觉行 → 每个视觉行拆成一个独立段落（闭合的 `a:p`，不跨行合并），行距用 `a:spcPts` 写死 → **断行位置 100% 由我们决定**。
代价：用户改字后不再自动重排；目标机缺字体时会变成**错误断行**（所以必须配字体策略）。

### 墙二：字体 —— 决定"换台机器会不会全篇错位"

- pptx **默认只写字体名，不嵌字体**（Slidev 官方文档明说）。目标机没有该字体 → 度量变化 → 即使硬断行也保不住字宽。
- **CJK 必须同时写 `a:latin` / `a:ea` / `a:cs`**：python-pptx 的 `font.name` 只写 `a:latin`，中文会掉到主题 `+mn-ea`（Windows 中文默认「等线」）；PptxGenJS v4.0.1 会把三者写成同一个 `fontFace`（源码 `pptxgen.cjs.js:5963`），但没有 latin≠ea 的 API。
- **嵌入在 OOXML 里可行但难**：`p:embeddedFontLst` + `ppt/fonts/*.fntdata` + rels + `[Content_Types]` 的 `application/x-fontdata`；但 **fntdata 是 EOT 容器而非裸 TTF/OTF**（[MS-OI29500 §2.1.32](https://learn.microsoft.com/en-us/openspecs/office_standards/ms-oi29500/ea097c57-5794-4624-b08e-017b47051b1d)），PptxGenJS 与 python-pptx **都不支持**，须自研后处理。
- **授权边界**：本机实测 fsType — Noto CJK = 0（可嵌入）、Heiti = 0、**Hiragino Sans GB = 8（不可嵌入）**；苹方/微软雅黑等商业字体同样不可嵌入。**默认字体集只放 OFL 字体（思源/Noto）。**

### 墙三：OOXML 表达力 —— 有些东西真的没有原语

| 有原生原语 | 无原生原语（只能元素级栅格或放弃） |
|---|---|
| 纯色/透明填充（`a:solidFill`+`a:alpha`） | 混合模式（`mix-blend-mode`） |
| 线性渐变（`a:gradFill/a:lin`）、径向（受限） | 模糊 / `filter` / `backdrop-filter` |
| 边框（`a:ln`）、圆角（`prstGeom roundRect`） | 多层阴影 / 内阴影 |
| 单层外阴影（`a:effectLst/a:outerShdw`） | 非对称圆角（要 `custGeom`） |
| 自由路径（`a:custGeom`） | 文字渐变 / WebGL / 3D 变换 |
| 图片裁剪（`a:blipFill`+`a:srcRect`） | 动画 / 切换 / SmartArt / OMML 公式（库层面全不支持） |
| 表格（`a:tbl`）、列表（`a:buChar`） | |

**降级原则**：**只做元素级降级，永不整页截图。** 且栅格前必须把将被矢量重画的文字隐藏掉，否则会出现"图上有字、上面又叠一层字"的双层 bug（Hasasasa 已把它写成硬规则）。

## 6. 本机原型实测（硬证据）

> 代码与完整数据：`prototype/`。栈：Node 26 + Playwright（系统 Chrome）+ PptxGenJS 4.0.1 + LibreOffice 26.8 + pdftoppm。

### 6.1 做了什么

5 页 1280×720 的 HTML（覆盖大标题、多行正文、圆角卡片、1px 细线、图片、SVG 图标、表格、渐变背景、半透明层）→ 逐元素量测 → 映射为原生对象 → 落盘 → 回渲逐页比对。

### 6.2 可编辑性统计（Lead 独立解包复核，不信任生成器自述）

| 指标 | 实测值 |
|---|---|
| 幻灯片尺寸 | `sldSz cx="12192000" cy="6858000"` ✅ |
| 形状 `p:sp` | 66 |
| 图片 `p:pic` | 3（**全是 HTML 里的真实图片**：logo / 照片 / 1px 探针） |
| 表格 `p:graphicFrame`+`a:tbl` | 1 + 1（原生表格） |
| 文本 run `<a:t>` | **68**（XML 内 1263 字符，非空白 1126） |
| **文本字符覆盖率** | **100.0%**（HTML 非空白 1126 → pptx `<a:t>` 非空白 1126，逐页均 100%；含表格单元格） |
| 自由路径 `a:custGeom` | **8**（8 个 SVG 图标全部原生，**0 个 PNG 降级**） |
| 原生渐变 `a:gradFill` | **2** |

### 6.4 回渲比对

| 页 | `diff>16` 占比 | `diff>48` 占比 | MAE |
|---|---|---|---|
| 1 | 4.26% | — | 5.35 |
| 2 | 5.35% | — | 5.85 |
| 3 | 4.16% | — | 3.71 |
| 4 | 3.67% | — | 2.83 |
| 5 | 2.88% | — | 2.73 |
| **全页** | **4.06%** | **2.97%** | **4.25** |

**按对象类型归因（这一步比像素差本身重要）**：

| 对象类型 | 差异面积占比 | 说明 |
|---|---|---|
| 文本区域 | **20.3%** | 字形边缘 + 基线偏移，**不是错位** |
| 形状 | 4.3% | 圆角/描边抗锯齿 |
| 图片 | 1.7% | 基本一致 |

**两条根因，都已量化并归入验收白名单**：

1. **字体加载（已修）**：LibreOffice headless 默认只加载自带 fontconfig，会把 `PingFang SC` 换成 `LinuxLibertineG` + `NotoSansCJKhk`。给 soffice 传 `FONTCONFIG_FILE` 后，PDF 内嵌字体变为 `PingFangSC-Regular/Semibold`，肉眼收敛。
2. **CJK↔拉丁边界间距（系统性差异，非 bug）**：`npm run fontprobe` 做了 7 字体对照——纯拉丁 `Δ = −0.9%`、纯 CJK `Δ = −1.1%`，而**中英混排对所有字体一律 +3.4%~4.3%**（3 个边界 × ≈7.5px ≈ 22.5px）。这正是 §5 墙一第 3 条的 LibreOffice 0.25em 行为。
3. **首行基线偏低 1–6px（中位 3px）**：PPTX 文本比 HTML 低，随 `line-height` 变化。**原型没有偷偷补偿**（`TEXT_Y_OFFSET = 0`），而是把它作为已知偏差写进 `pixel.json`——因为补偿在 LibreOffice 上"对"，到真 PowerPoint 上可能"错"。

→ **结论：LibreOffice 只能当"包完整性 + 结构一致性 + 明显崩坏"的守门员，不能当"与 PowerPoint 逐像素一致"的裁判。**

## 7. 结论与建议

### 7.1 选型结论

| 问题 | 结论 |
|---|---|
| 走哪条路线？ | **路线 C：量测重建**。A 不可编辑、B 不可控、D 版式被锁死、E 放弃 HTML 的价值 |
| 画布基准？ | **1280×720 px ↔ 13.333×7.5 in ↔ 12192000×6858000 EMU**（= PowerPoint 默认宽屏）。**不要用 Anthropic 的 720×405pt**，那是 PptxGenJS 默认 10in 布局的副产物 |
| 写入层？ | **PptxGenJS 起步**（生态最大、API 最全），但要做适配层隔离 + 后处理补齐（gradFill / custGeom / 字体嵌入 / DEFLATE），并预留"直写 DrawingML"的替换路径 |
| 能不能用现成库？ | 可以用 MIT 的（dom-to-pptx / Hasasasa / Design-Arena）当**参考**，但**不建议直接依赖**：都缺 Office 打开回归与字体嵌入；presenton 导出核心闭源；Anthropic 系代码许可不可用 |
| 承诺几级可编辑？ | **L2**，并显式声明不做动画/母版/公式 |
| 精确怎么承诺？ | 几何精确 + 语义精确**可以写进 SLA**；排版精确写"断行位置与浏览器一致（硬断行模式）"，不写"逐像素相同" |

### 7.2 产品形态建议：双层模型

- **编辑层**：用户/AI 写**受约束 HTML**（语义标签 + token + `data-ppt-*` 标注）+ 组件库（每个组件带导出语义）。
- **导出层**：确定性编译器（量测 → IR → 映射 → 后处理），对白名单外样式**逐元素降级并出报告**，**永不整页栅格化**。
- **验收层**：L0 包合法 → L1 结构断言 → L2 回渲结构差 → L3 像素趋势（同引擎回归）。
- **自由 HTML 不是不能支持**，但必须走"高级模式 + 显式 lossy 同意"；默认路径应是受约束组件。
