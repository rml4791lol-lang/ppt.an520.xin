# 评审判定线：规格轴与标准轴

> 适用：任何“能不能合入 / 能不能关票”的评审，人或 agent 一律按本文两轴判定。
> 关联：门命令见 `AGENTS.md` 与 `.agents/skills/anppt-gate`；流程纪律见 `docs/DEVELOPMENT.md`；票据在本仓库 GitHub Issues。

## 1. 规格轴：票面验收标准

**判定线**：票上每一条 Acceptance criterion 都有一条**可复现的证据**（命令 + 输出、截图、链接），且证据与断言匹配。

- 没有证据 = 未通过；证据与断言不匹配（例如断言“会失败”却只贴了成功输出）= 未通过。
- 不接受“实现者说做过”“代码看起来对”作为证据。
- 允许部分完成的唯一情形：票面写明分期，且本期 AC 全部有证据；否则一律不通过。
- 规格轴的“可接受遗留” = AC 之外的改进项，或票面明确 Out of Scope 的事项。必须写进票的评论，且不阻塞本票。
- 规格轴不通过 → 不得关票；**不得用“标准轴全绿”替代未完成的 AC**。

## 2. 标准轴：仓库契约 + 门

**判定线**（任一条不满足即阻断）：

1. **门全绿**：`npm run gate` 退出码 0。`gate:fast` 不能替代全集（它跳过两套测试与 build）。
2. **分层与模块纪律**：`docs/DEVELOPMENT.md` §1 的依赖方向；由 lint 的 `import/no-restricted-paths` 机器执行，新增例外必须登记原因。
3. **最小改动**：只动任务直接要求的文件；不顺手重构、不批量改格式、不删无关注释。
4. **注释纪律**：代码只留“为什么”；机制、口径、坑写进 docs/ 对应小节。
5. **测试与数字**：业务逻辑改动同步加/改断言；断言数变化同步 `README.md` 与 `docs/DEBUG-HANDBOOK.md` §8；新护栏必须带“喂坏夹具会红”的证据，而不只是成功路径。
6. **无危险模式**：不提交密钥、`.env`、本地数据、临时夹具；不静默绕过门（`--no-verify` 只允许人按紧急操作使用，且 CI 兜底）。
7. **文档同步**：被改动的机制在对应文档有记录（系统全貌 → `docs/DEBUG-HANDBOOK.md`；日志/健康 → `docs/LOGGING.md`；流程 → 本文或 `docs/DEVELOPMENT.md`）。

标准轴的“可接受遗留”只允许**已登记**的技术债：票或 docs 里有出处、有删除条件、不扩大爆炸半径。未登记的一律按阻断处理。

## 3. 阻断项优先

标准轴存在任一阻断项时，**规格轴不得单独放行**。结论只有三种：

- **阻断**：列出每个阻断项（严重度 + 位置 + 证据 + 修法），票不得关闭。
- **有条件通过**：无阻断项，但有非阻断建议；建议单列，不混进结论。
- **通过**：两轴都过，逐条 AC 附证据指针。

唯一例外：规格轴未通过（票没做完）时不必等标准轴结论——直接拒绝，避免“标准轴绿了所以票算完成”的偷换。

## 4. 评审结论的写法

每条发现固定四段：严重度（阻断/建议）、位置（`file:line` 或票号）、证据（实际命令与输出）、修法。

结论行固定为：

```text
结论：阻断 | 有条件通过 | 通过
规格轴：通过 / 未通过（AC 逐条打勾 + 证据指针）
标准轴：通过 / 阻断（阻断项列表）
```

## 5. 为什么写下来

2026-10-28 两个评审 agent 对同一份代码给出相反结论（一个“可接受遗留”、一个“不能合入”）。分歧不在事实，而在判定线没有写下来：规格轴回答“票做完了吗”，标准轴回答“能合入吗”。两者都能被证据判定；谁也不能替谁签字。
